# 正式上线与恢复

本项目当前运行后端仍是 SQLite + 本地图片。下面准备好了持久化部署、邮件、备份和监控入口；尚未连接 Supabase，也未部署到外网。Docker 配置未在本机实际构建。

## 现有数据

默认数据位于 `storage/data.sqlite` 和 `storage/uploads/`，现有数据已迁入该目录。设置 `TP_DATA_DIR` 后，两者必须一起搬到新目录，不能只改环境变量，否则会启动一个新库。`public/media/` 是随代码部署的静态资源。

本地继续使用 `npm start`。需要环境文件时，复制 `.env.example` 为 `.env` 并修改配置，服务启动会自动读取。示例的数据目录与当前实际使用的 `storage/` 一致。

## 正式服务

- 使用 HTTPS 反向代理，设置真实 `PUBLIC_SITE_URL`、`COOKIE_SECURE=1`；仅在确实经过一层可信代理时设置 `TRUST_PROXY=1`。
- 首次新建生产数据库需设置至少 12 位 `ADMIN_INITIAL_PASSWORD`；已有数据库继续使用其已有管理员密码，部署前须修改演示默认密码。
- Docker 镜像使用 `/data` 保存数据库和上传图片、`/backups` 保存完整备份，两个目录都需要挂载持久化卷。容器只提供 Node 服务，域名、TLS 和反向代理需要在托管环境配置。
- `/healthz` 为不含私密数据的可用性检查。后台「设置」可查看最近备份与进程内异常数量。外部监控和报警收件人需在托管平台设置。

## 忘记密码

后台「设置」填写站点 URL、SMTP 主机、端口、账号、密码、From，先保存再发送测试邮件。也可用 `SMTP_HOST/PORT/USER/PASS/FROM` 环境变量；环境变量的清除需要修改部署配置。

用户点击登录页「忘记密码」，输入注册邮箱，收到 1 小时有效、仅能使用一次的链接。重置后旧会话与其他重置链接全部失效。未配置发信条件时界面会明确提示联系客服。

管理员可在「用户管理」中重置用户密码，旧登录立即失效。应先确认用户身份，再通过其可信联系方式传递临时密码；平台不读取或发送原密码。管理员自己忘记密码时，由另一个管理员在「后台员工」中重置；只有一个管理员时需服务器运维协助，不要删除数据库。

## 备份与恢复

服务默认启动后备份一次，此后每 24 小时备份一次。`TP_AUTO_BACKUP=0` 可关闭；离线手工备份用 `npm run backup`。备份包含一致性数据库快照、上传文件和 SHA-256 清单。不会自动删除旧备份，应安排容量管理，并将备份另存到其他设备或对象存储；同机备份不能应对整台服务器损坏。

校验：`node scripts/backup.js verify <备份目录>`。

恢复：先停止服务，运行 `node scripts/backup.js restore <备份目录> <新的空数据目录>`，再将 `TP_DATA_DIR` 指向恢复目录启动。恢复工具拒绝覆盖已有内容。请勿向运行中的数据库文件直接覆盖备份。

## PostgreSQL / Supabase

正式数据库选择仍需确定。当前代码使用 SQLite 同步查询、迁移和日期语法，不能仅添加 Supabase URL 就切换数据库。迁移需要：备份、导出并校验数据、转换表结构和查询层、接入图片存储、在测试项目核对登录/审核/定时发布/恢复流程，最后切换正式站点。

这一步需要目标项目、部署地区、连接方式和存储权限；不要把数据库密码或 service role key 放进前台 JS 或提交到仓库。付费套餐和域名购买需要由账户所有者决定。

## 发布验收

运行 `npm test`；浏览器回归用 `node tests/browser-smoke.js --capture`。后者仅写临时测试数据库。上线后还需在真实域名实际验证邮件投递、HTTPS、图片持久化、备份异机保存和监控报警。
